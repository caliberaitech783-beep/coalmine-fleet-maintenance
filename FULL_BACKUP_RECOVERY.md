# Full Backup recovery

Keep the private recovery key offline, outside Azure and GitHub. The server only has the public key. Losing the private key makes encrypted backups unusable. Keep a second protected copy and test it.

1. On a clean recovery computer, install Node.js 22. Obtain this repository's recovery scripts and install dependencies (`npm ci`).
2. Decrypt: `node scripts/decrypt-full-backup.mjs full-backup.enc recovery-private.pem recovery.zip`. Authentication failure means the file/key is invalid; never use partial output.
3. Extract recovery.zip into a protected directory. Check manifest.json component coverage and SHA-256 checksums. A Partial archive is not a complete recovery set.
4. Restore the repository: `git clone application.bundle recovered-app`. Check out the manifest's deployed commit. application-source.zip is the source snapshot fallback.
5. Decrypt azure-hosting.enc with the same script, specifying an output .json filename. This contains the Azure resource export, detailed resource/configuration inventory, app settings, slot configuration and PITR status. Inspect template export warnings; exported templates can require repair and parameters before redeployment. External DNS zones, Key Vault secret values, provider account recovery controls, private certificate keys and external storage contents need separate protection when applicable; coverage lists these limits.
6. Recreate Azure resources, networking and domain/certificate bindings using the inventory. Re-enter protected environment settings from environment.json and the Azure snapshot. Rotate credentials after a security incident. Recreate managed identities/RBAC against their new principal IDs.
7. Create an empty PostgreSQL database with the compatible server version/extensions. Run `npm ci` and the application once with scheduled jobs disabled to initialize the schema. Stop the application. Restore: `node scripts/restore-database.mjs --input database.ndjson.gz --database-url "postgres://..." --yes`. The portable archive contains public tables and sequences, not SQL roles/schema/functions/extensions; use matching application migrations. Do not expose credentials in shared shell history. For native database.dump use pg_restore instead; SQL roles/grants must be reviewed separately.
8. Restore separately retained media/session exports and external storage when required. Current media held in public database tables is included in database.ndjson.gz. Deleted media cannot be reconstructed from a newer database export.
9. Build/deploy the recorded application version. Verify /api/health, /api/app-version, table counts, login, permissions, attachments, reports and provider connections in isolation before routing traffic. Enable production schedules only after verification.
10. Azure PITR is a separate Azure-managed recovery mechanism, not a downloadable WAL backup. Use the recorded server ID, earliest restore time and retention to restore a NEW server through Azure. Reconnect the application to it. Latest recoverable time may lag; zero data loss is not guaranteed.

Each bundle has component status, file hashes, versions and recovery instructions. Full Backup retains its own history and IST schedule independently of the existing database schedule. Azure snapshot collection runs separately through GitHub OIDC. An old/missing snapshot or missing Git history produces Partial, never Completed. GitHub encrypted backup artifacts provide a second location with finite retention; additionally download encrypted copies to an offline/company-controlled location. GitHub/ Azure account compromise is not covered by keeping copies only in those accounts.
